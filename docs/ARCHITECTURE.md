# ARCHITECTURE — 架构总纲

> **状态**：设计定稿 · 对齐决策 #1 · 活文档 · 最后更新 2026-07-30
> 整个项目的**锚**。接手先读这一份，建立全局观。它定义"什么不能动"（内核）和"什么可以随便加"（模块）。

---

## 0. 一句话概括

一个**用于学习 agent 底层逻辑的、可插拔模块化 agent 框架**。设计信条：

> **健壮 = 极小且稳定的内核 + 想得极全的钩子点 + 数量不限的可插拔模块。**

内核克制到极致，所有"能力"都是模块，通过钩子挂载，用不到的模块不加载。

---

## 1. 分层总览

```
┌────────────────────────────────────────────┐
│  Frontend 前端（可替换）：CLI（先做）/ Web（未来） │
│  职责：显示内核每一步事件；接收用户输入            │
└───────────────────────┬────────────────────┘
                        │ 只依赖内核的公开事件流
┌───────────────────────▼────────────────────┐
│  Kernel 内核（稳定、极简、不轻易改）             │
│  ① Agent Loop  主循环（思考→行动→观察）         │
│  ② Message Protocol 统一消息协议               │
│  ③ Provider 抽象  统一各模型商 API 方言         │
│  ④ Hook System  钩子系统 ← 模块化的全部秘密     │
│  ⑤ Tool Registry  工具注册与调度               │
│  ⑥ Context  贯穿一次运行的共享状态              │
└───────────────────────┬────────────────────┘
                        │ 模块通过钩子挂载，内核不认识任何具体模块
   ┌────────┬───────────┼─────────┬──────────┐
 [RAG]  [Memory]  [Planner]  [Approval]  [Budget] ...  可插拔
```

**铁律：内核不认识任何具体模块。** 内核只知道"在某个时机广播一个事件，谁监听我不管"。若"为加某模块必须改内核"，说明钩子点漏了——正确做法是补钩子点，而非让内核认识模块。

## 2. 内核六大件

### ① Agent Loop 主循环

```
run(用户输入):
    把输入加入对话历史
    loop:
        [钩子] on_iteration_start
        [钩子] before_model_call     ← RAG/记忆在这里注入上下文
        response = provider.chat(历史, 可用工具)
        [钩子] after_model_call
        if 模型要调用工具:
            [钩子] before_tool_call   ← 审批/预算在这里拦截
            result = 执行工具
            [钩子] after_tool_call
            把结果加入历史; continue
        else:
            [钩子] on_iteration_end / on_run_end
            return 答复
        [安全阀] 超过最大迭代次数 → 强制停止
```

主循环**本身不做任何"聪明"的事**（不做 RAG、记忆、规划），只负责推进循环、在关键时机广播钩子事件。所有聪明都来自模块。

### ② Message Protocol 消息协议

框架内部流通**统一消息格式**，与任何模型商无关；provider 层负责翻译成各家方言再翻回来。基本角色：`system`/`user`/`assistant`/`tool`。这是最需要想周全的数据结构（记忆要序列化它、RAG 要往里插内容、多 agent 要传递它）。详见 `MESSAGE_PROTOCOL.md`。

### ③ Provider 抽象

统一接口屏蔽 OpenAI/Anthropic/Ollama 差异。内核只调这个接口，永不直接碰厂商 SDK。至少能：给历史+工具返回下一步响应、支持流式、报告 token 用量、声明自身能力。先实现一家（OpenAI 兼容，决策 #9），其余留骨架。详见 `PROVIDER.md`。

### ④ Hook System 钩子系统 ★核心★

整个项目最重要的部分，见 `HOOKS.md`。

### ⑤ Tool Registry 工具注册与调度

工具 = 名字 + 描述 + 参数 schema + 执行函数。负责注册、生成模型可理解的 schema、调度执行、参数校验、错误捕获（工具报错变成能喂回模型的消息，不让程序崩）。工具本身也可由模块提供（如 RAG 注册"检索"工具）。

### ⑥ Context 对象

一次 `run` 期间贯穿始终的共享状态，在所有钩子间传递。至少持有：对话历史、可用工具集、运行元数据（迭代计数/token 累计/开始时间）、一个**模块可自由读写的共享区**（module scratch space）。Context 是模块与内核、模块与模块间传递数据的主通道（铁律 5）。

## 3. 钩子系统概览

在 agent 生命周期的每个关键时机设一个钩子点，只要缝隙都被覆盖，任何模块都能找到地方挂，无需改内核。

**钩子点**（详见 HOOKS.md）：`on_run_start` / `on_iteration_start` / `before_model_call` / `after_model_call` / `before_tool_call` / `after_tool_call` / `on_iteration_end` / `on_run_end` / `on_error` / `on_tool_error`。

**两种权力级别**：
- **观察者（Observer）**：只读，不改流程；多个观察者顺序无关；崩了零影响。
- **拦截者（Interceptor）**：可改数据或中断流程（RAG 注入、审批中断、缓存替换）。更强也更危险，因此需要**明确优先级**和**"改了什么"的契约**。

## 5. 关键设计原则（写代码时反复对照）

1. 内核不认识任何具体模块。违反即架构腐化。
2. 内核极简。加东西前先问"这能不能做成模块？"
3. 一切能力皆模块，可插拔、可隐藏、优雅降级；缺某模块不应导致崩溃。
4. 消息协议与厂商无关；厂商差异只在 provider 层。
5. 钩子点宁全勿缺；没人监听的钩子零成本空转。
6. 拦截者必须有明确优先级和"改了什么"的契约。
7. 每个模块可独立测试，每层有可跑的 demo。
8. 工程规范 = 类型标注 + 错误处理 + 日志 + 测试（具体见 ROADMAP）。
