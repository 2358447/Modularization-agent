# ARCHITECTURE — 架构总纲

> 本文件是整个项目的**锚**。任何 AI 或人接手本项目，先读这一份。
> 它定义了"什么不能动"（内核）和"什么可以随便加"（模块）。
> 状态：**草稿 v0.1，待 owner 审阅**

---

## 0. 一句话概括

这是一个**用于学习 agent 底层逻辑的、生产级的、可插拔模块化 agent 框架**。

设计信条：

> **健壮 = 极小且稳定的内核 + 想得极全的钩子点 + 数量不限的可插拔模块。**

内核克制到极致，所有"能力"都是模块，通过钩子挂载。用不到的模块不加载。

---

## 1. 分层总览

```
┌────────────────────────────────────────────────────┐
│  Frontend 前端（可替换）                              │
│  · CLI（第一个实现）                                  │
│  · Web（未来，作为另一个前端插件）                      │
│  职责：把内核每一步的事件"显示"出来；接收用户输入          │
└───────────────────────┬────────────────────────────┘
                        │  只依赖内核的公开事件流
┌───────────────────────▼────────────────────────────┐
│  Kernel 内核（稳定、极简、不轻易改）                    │
│                                                      │
│  ① Agent Loop      主循环（思考→行动→观察）             │
│  ② Message Protocol 消息协议（统一的对话数据结构）       │
│  ③ Provider 抽象    统一不同模型商的 API 方言           │
│  ④ Hook System     钩子系统 ← 模块化的全部秘密          │
│  ⑤ Tool Registry   工具注册与调度                      │
│  ⑥ Context 对象     贯穿一次运行的共享状态              │
└───────────────────────┬────────────────────────────┘
                        │  模块通过钩子挂载，内核不认识任何具体模块
     ┌─────────┬────────┼────────┬─────────┬──────────┐
     ▼         ▼        ▼        ▼         ▼          ▼
  [RAG]    [Memory]  [Planner] [Observ.] [Approval] [Budget] ...
  可插拔     可插拔    可插拔     可插拔     可插拔      可插拔
```

**铁律：内核不认识任何具体模块。** 内核只知道"在某个时机广播一个事件，谁监听我不管"。这是整个架构可扩展的根基。如果哪天你发现"为了加某模块必须改内核"，那说明**钩子点漏了**，正确做法是补一个钩子点，而不是让内核认识那个模块。

## 2. 内核六大件

### ① Agent Loop 主循环

最底层就是这个循环：

```
run(用户输入):
    把输入加入对话历史
    loop:
        [钩子] 迭代开始
        [钩子] 请求模型前  ← RAG/记忆在这里注入上下文
        response = provider.chat(历史, 可用工具)
        [钩子] 收到模型响应后
        if 模型要调用工具:
            [钩子] 工具执行前  ← 审批/预算在这里拦截
            result = 执行工具
            [钩子] 工具执行后
            把结果加入历史
            continue
        else 模型给出最终答复:
            [钩子] 迭代结束
            [钩子] 运行结束
            return 答复
        [安全阀] 超过最大迭代次数 → 强制停止
```

主循环**本身不做任何"聪明"的事**（不做 RAG、不做记忆、不做规划）。它只负责推进循环、在关键时机广播钩子事件。所有聪明都来自模块。

### ② Message Protocol 消息协议

整个框架内部流通的是**统一的消息格式**，与任何模型商无关。Provider 层负责把它翻译成各家 API 的方言、再把各家的响应翻译回来。

消息的基本角色：`system` / `user` / `assistant` / `tool`。
一条 assistant 消息可能包含：思考文本、以及零或多个工具调用请求。
一条 tool 消息承载：某个工具调用的执行结果（或错误）。

> **这是最需要现在想周全的数据结构**——因为记忆模块要序列化它、RAG 要往里插内容、多 agent 要传递它、可观测性要记录它。它必须从第一天就为未来所有模块留好位置。详细字段设计见 `docs/MESSAGE_PROTOCOL.md`（待写）。

### ③ Provider 抽象

定义一个统一接口，屏蔽 OpenAI / Anthropic / Ollama 等的差异。内核只调用这个接口，永远不直接碰任何厂商 SDK。

接口至少要能回答：
- 给你历史消息 + 可用工具，返回模型的下一步响应（含工具调用）
- 支持流式输出（前端要实时显示"思考"）
- 报告 token 用量（预算模块要用）
- 声明自己的能力（是否支持原生 function calling、是否支持流式、上下文窗口多大）

先实现一家跑通，其余留骨架。详见 `docs/PROVIDER.md`（待写）。

### ④ Hook System 钩子系统 ★核心★

**这是整个项目最重要、最需要设计到位的部分。** 单独在第 3 节详述。

### ⑤ Tool Registry 工具注册与调度

- 工具的注册（一个工具 = 名字 + 描述 + 参数 schema + 执行函数）
- 自动把工具描述生成模型能理解的 schema
- 调度执行、参数校验、错误捕获（工具报错要变成能喂回模型的消息，而不是让程序崩）

工具本身也可以由模块提供（比如 RAG 模块会注册一个"检索"工具）。

### ⑥ Context 对象

一次 `run` 期间贯穿始终的共享上下文对象，在所有钩子间传递。它至少持有：
- 当前对话历史
- 当前可用工具集
- 本次运行的元数据（迭代计数、token 累计、开始时间等）
- 一个**模块可自由读写的共享区**（module scratch space），让模块之间、以及模块的多次钩子调用之间能存取状态

Context 是模块与内核、模块与模块之间传递数据的主通道。

## 3. Hook System 钩子系统（核心设计）

### 3.1 设计目标

让**未来任何还没想到的模块**都能挂载，而无需修改内核。实现方式不是"预先写好所有接口"，而是：

> **在 agent 生命周期的每一个关键时机，都设一个钩子点。只要缝隙都被覆盖，任何模块都能找到地方挂。**

### 3.2 钩子点清单（生命周期事件）

> 这里体现你要的"想得极全"。宁可先定义、暂时没人用，也不要漏。用不到的钩子零成本（没模块监听就是空转）。

| 钩子点 | 触发时机 | 典型使用模块 |
|--------|---------|-------------|
| `on_run_start` | 一次 run 刚开始 | 可观测性、预算初始化、会话记忆加载 |
| `on_iteration_start` | 每轮循环开始 | 可观测性、死循环检测 |
| `before_model_call` | 组装好消息、即将发给模型前 | **RAG（注入检索结果）**、记忆（注入相关记忆）、上下文压缩、prompt 加工 |
| `after_model_call` | 收到模型响应后 | 可观测性、成本统计、响应缓存 |
| `before_tool_call` | 即将执行某个工具前 | **审批（人工确认）**、预算（拦截超支）、参数二次校验、限流 |
| `after_tool_call` | 工具执行完毕后 | 可观测性、结果缓存、结果裁剪（大输出压缩） |
| `on_iteration_end` | 每轮循环结束 | 记忆（决定存什么）、反思、进度更新 |
| `on_run_end` | 一次 run 正常结束 | 可观测性、记忆落盘、成本汇总 |
| `on_error` | 任意环节抛异常 | 可观测性、错误恢复、降级策略 |
| `on_tool_error` | 工具执行失败 | 错误恢复、重试策略 |

（清单可增补。增补钩子点属于"内核变更"，需走 `DECISIONS.md` 记录。）

### 3.3 钩子的两种"权力"级别

不同模块想介入的深度不同，钩子分两级：

1. **观察者（Observer）**：只读，不能改流程。例：可观测性只是记录。多个观察者互不干扰，执行顺序不影响正确性。
2. **拦截者（Interceptor）**：可以修改流经的数据，甚至中断流程。例：
   - RAG 在 `before_model_call` **修改**要发送的消息（注入上下文）
   - 审批在 `before_tool_call` **中断**流程（用户拒绝则不执行该工具）
   - 上下文压缩在 `before_model_call` **替换**历史消息

拦截者更强大也更危险，因此需要：**明确的执行顺序（优先级）** 和 **清晰的"我改了什么"契约**。

### 3.4 执行顺序（优先级）

同一个钩子点上挂了多个模块时，按**优先级数字**排序执行。这必须显式可控，否则"RAG 先注入还是压缩先执行"会变成玄学。优先级规则写入 `MODULES.md`。

### 3.5 内核与模块的契约（Module 接口）

一个模块 = 声明"我要监听哪些钩子、优先级多少、被触发时做什么"。模块可以：
- 注册钩子回调
- 注册工具
- 在 Context 的共享区读写自己的状态
- 声明依赖（比如"记忆模块依赖某个存储后端"）

模块**不能**：直接调用内核内部、不能绕过钩子改主循环、不能假设别的模块一定存在（要优雅降级）。

模块的生命周期：`加载 → 注册钩子/工具 → 运行期被触发 → 卸载/清理`。

## 5. 关键设计原则（写代码时反复对照）

1. **内核不认识任何具体模块。** 违反即架构腐化。
2. **内核极简。** 想往内核加东西前，先问"这能不能做成模块？"
3. **一切能力皆模块，可插拔、可隐藏、优雅降级。** 缺某模块不应导致崩溃。
4. **消息协议与厂商无关。** 厂商差异只存在于 provider 层。
5. **钩子点宁全勿缺。** 生命周期缝隙必须有钩子。
6. **拦截者必须有明确优先级和"改了什么"的契约。**
7. **每个模块可独立测试，每层有可跑的 demo。**
8. **生产级 = 类型标注 + 错误处理 + 日志 + 测试**（具体清单见 ROADMAP）。
