## #1 · 2026-07-30 · 内核采用同步（synchronous）实现，而非 async

**背景**：内核主循环、provider 调用、工具执行的执行模型需在动第一行代码前确定，因为它渗透内核每一行，后期改动成本极高。

**决策**：内核用**同步**代码实现。

**理由**：
- 项目首要目标是**看清 agent 底层逻辑**，同步代码调用栈清晰、debug 直接，最利于学习。
- owner 时间充足、不赶工，无需为并发性能提前买单。
- 并行工具调用、流式输出等需要并发的能力，等真正需要时再用线程/进程或局部重构引入，并把"同步→异步重构"本身当作一节学习课。

**影响**：
- provider 接口、主循环、钩子回调、工具执行签名全部为同步。
- 流式输出初期用同步生成器（generator）实现即可满足 CLI 实时显示。

**状态**：生效。

## #2 · 2026-07-30 · 项目纳入 git 版本管理

**背景**：需要可溯源的变更历史，防止"小修改淹没大修复"，也为将来可能的开源做准备。

**决策**：从项目初期即初始化为 git 仓库，默认分支 `main`。

**理由**：
- git log 本身就是最可靠的文档/代码变更记录，`git log <file>` 可追溯任意文件的每次变更。
- 配 `.gitignore` 从第一天防止 API key、缓存、虚拟环境误提交（生产级基线）。
- 配 `.gitattributes` 统一换行为 LF，消除跨平台噪音。

**影响**：每次有意义的改动都应是一个带清晰 message 的 commit。

**状态**：生效。

## #3 · 2026-07-30 · 文档分层治理规则

**背景**：owner 提出——若文档可随意修改，重要修复会被淹没、无法溯源。

**决策**：文档按性质分两类，分层治理：

- **活文档**（描述"系统现在是什么样"）：`ARCHITECTURE.md`、`HOOKS.md`、`MESSAGE_PROTOCOL.md`、`MODULES.md`、`PROVIDER.md`、`ROADMAP.md`。可更新、可覆盖旧内容；变更历史靠 git 追踪；每份顶部标注 `状态` 与 `对齐的决策编号`。
- **账本文档**（记录"发生过什么、为何如此"）：`DECISIONS.md`、`PROGRESS.md`。**只追加，永不删改**。

**规则**：任何"改变了架构约定"的变更，必须同时做到三件事：① 更新相关活文档 ② 在 `DECISIONS.md` 追加一条 ③ 一个清晰的 git commit。琐碎变更（错别字等）仅需 git commit，不占用 DECISIONS。

**理由**：区分"当前真相"与"历史账本"，既保持活文档简洁反映现状，又让重大变更有不可淹没的追溯路径。

**影响**：写入 `CLAUDE.md` 作为所有未来接手者必守的元规则。

**状态**：生效。

## #4 · 2026-07-30 · 文档分层加载 + 模块技术盲区速查

**背景**：owner 提出两点担忧——① 文档越来越多，AI 接手若全读会挤占上下文；② AB 混合模式下核心逻辑由 owner 写，撞进知识盲区易卡住、打断学习节奏。

**决策**：
1. **文档三层加载**：第 0 层必读（CLAUDE.md + PROGRESS 最新一条）；第 1 层开工前扫一遍（ARCHITECTURE.md）；第 2 层按需查阅（其余 docs，动到相关模块才读对应份，DECISIONS 仅在设计冲突时查）。
2. **模块速查惯例**：每个代码模块开工时先产出 `<模块目录>/CHEATSHEET.md`，仅收录该模块实际用到、owner 可能不熟的技术点（用途 + 最小例子 + 出现位置），定位为"陪练参考卡"而非语法教程。

**理由**：
- token/延迟成本只来自 LLM 调用，与文档量无关；但文档若强制全读会挤占 AI 上下文、抬高接手成本。分层加载把接手成本摁到最低。
- 速查就地消解盲区，避免 owner 中断学习节奏去外部检索，且"只写盲区"符合按需原则。

**影响**：写入 `CLAUDE.md`（〇节文档加载规则 + 协作契约第 6 条）。

**状态**：生效。

## #5 · 2026-07-30 · 文档写入规则（读规则的对称补充）

**背景**：owner 指出此前只规定了"读文档"的规则，缺"写文档"的规则——AI 可能该更新的活文档不更新（文档与代码脱节腐烂），或该追加的账本跑去改（破坏溯源）。

**决策**：确立文档写入规则，写入 `CLAUDE.md` 〇·补节：
1. **改 vs 追加**：活文档只能改（覆盖，反映现状）；账本文档（DECISIONS/PROGRESS）只能追加，永不改旧条目。
2. **写入触发时机**（表格化）：改架构约定→DECISIONS+活文档+commit 三件套；工作收尾→追加 PROGRESS；代码使活文档过时→立即改活文档；新开模块→建 CHEATSHEET；琐碎修改→仅 commit。
3. **两条硬约束**：代码与其对应文档同一 commit 落地；改活文档同步更新顶部状态/对齐决策编号/最后更新。
4. **兜底判断**：拿不准是否记录时，以"他人/另一 AI 不知情是否会走弯路或重复讨论"为准。

**理由**：读规则控制接手成本，写规则防止文档腐烂与账本篡改，二者合起来才构成完整的文档治理闭环。

**影响**：`CLAUDE.md` 新增〇·补节。此后所有写文档行为以此为准。

**状态**：生效。

## #6 · 2026-07-30 · Git 使用规则与分支策略

**背景**：此前对 git 的要求散落各处，缺集中规则。owner 已创建 GitHub 远程仓库 `https://github.com/2358447/Modularization-agent`。

**决策**：确立 git 规则，写入 `CLAUDE.md` 五·补节：
1. 提交时机：一个逻辑完整改动 = 一个 commit；不把跑不起来的代码提交到 main。
2. commit message 格式：`类型: 简述`（feat/fix/docs/refactor/test/chore）。
3. **分支策略采用 A：main + 功能分支**。main 永远可运行；新模块/大改动走 `feat/<名字>` 分支，审过验收后合并回 main；合并点作为"章节里程碑"服务开源可讲述性。
4. push：main 有实质更新即推 origin；对外发布若涉新目标需 owner 授权（推 origin/main 已授权）。
5. 铁律：密钥走环境变量/.env，绝不进提交。

**理由**：main+功能分支符合"一次一个模块"的节奏，天然形成里程碑历史，且是生产级协作标准姿势，owner 借此练习分支流程（届时配 CHEATSHEET）。

**影响**：下一步写代码起即按此分支流程操作。

**状态**：生效。

## #7 · 2026-07-30 · 活文档写作风格：客观、无对话痕迹

**背景**：`HOOKS.md` 初稿混入"owner 已拍板""呼应你问过的"等对话腔，稀释专业度、对不了解上下文的接手者无价值。

**决策**：活文档只陈述客观事实（系统是什么、为什么这么设计），不带对话痕迹。"某决定由谁何时拍板"属溯源信息，归入 `DECISIONS.md`，不散落活文档正文。

**理由**：活文档面向未来不了解上下文的接手者；溯源与事实分离，各归其位（活文档=当前真相，DECISIONS=历史账本）。

**影响**：写入 `CLAUDE.md` 文档写入规则；已据此清理 HOOKS.md。

**状态**：生效。

## #8 · 2026-07-30 · 多工具结果内部粒度：一对一（一条 tool 消息一个结果块）

**背景**：MESSAGE_PROTOCOL 中"多个工具结果如何组织"存在两种候选（多条消息 vs 一条多块）。经联网核实两家 API 要求。

**决策**：内部统一"一条 tool 消息 = 一个 tool_result 块"（一对一），合并/拆分交给 provider 层。

**依据**（官方文档核实）：
- OpenAI：每个 `tool_call_id` 对应一条独立 `role:tool` 消息。内部一对一 → 直接映射。
- Anthropic（docs.claude.com/parallel-tool-use 明确）：并行工具所有结果须在**同一条 user 消息**内作为多个 tool_result block，且结果前无文本，否则破坏并行机制。内部一对一 → provider 聚合。

**理由**：一对一粒度最细最好推理；契合 HOOKS §C"每工具独立走钩子、执行完即产出结果"；两翻译方向均可行，合并比拆分易实现。

**影响**：MESSAGE_PROTOCOL §3/§4.1 已定；provider 层需实现 Anthropic 方向的聚合（结果前无文本）。

**状态**：生效。

## #9 · 2026-07-30 · 联网方式：内置 WebSearch/WebFetch 不可用，走本地代理 127.0.0.1:7890

**背景**：内置 WebSearch/WebFetch 在本环境被网络策略阻断（搜索返回空、抓取报错）。owner 提示本地有代理运行。

**决策**：需要联网核实/查资料时，通过本地 HTTP 代理 `http://127.0.0.1:7890`（Clash）用 `curl -x` 访问，而非依赖内置 web 工具。

**理由**：实测该代理可连通外网（成功抓取 docs.claude.com 等）。内置 web 工具走独立通道，未使用该代理，故不可用。

**影响**：未来 AI 需联网时，先用 `curl -x http://127.0.0.1:7890 <url>`。端口若变化需重新探测（常见：7890/7897/1080/10809）。代理是否运行取决于 owner 本地环境，不保证长期可用。

**状态**：生效（依赖 owner 本地代理运行）。
