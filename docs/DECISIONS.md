# DECISIONS — 决策日志

> 账本文档，追加式：每个影响全局的决策记一条。目的是让接手者知道"为什么是这样"，避免重复讨论已定的事。
> 格式：编号 · 决策 · 理由 · 状态。

---

## #1 · 内核采用同步实现，而非 async

**决策**：内核主循环、provider 调用、工具执行全部同步。
**理由**：项目首要目标是看清 agent 底层逻辑，同步代码调用栈清晰、debug 直接。并行工具/流式等需要并发的能力，等真正需要时再用生成器/线程引入，并把"同步→异步重构"本身当作一节学习课。
**注**：同步 ≠ 确定性；LLM 调用本不可复现，不含"可复现/禁随机源"约束。
**状态**：生效。

## #3 · 文档分层治理规则

**决策**：文档分两类——**活文档**（ARCHITECTURE/HOOKS/MESSAGE_PROTOCOL/MODULES/PROVIDER/ROADMAP，描述现状，可覆盖更新）与**账本文档**（DECISIONS/PROGRESS，只追加）。改变架构约定的变更须三件事一起做：改活文档 + 追加 DECISIONS + 一个清晰 commit。
**理由**：区分"当前真相"与"历史账本"，让重大变更有不可淹没的追溯路径。
**状态**：生效（细则见 CLAUDE.md）。

## #4 · 文档分层加载 + 模块技术盲区速查

**决策**：① 接手时分层读——必读 CLAUDE.md + PROGRESS 最新条；开工前扫 ARCHITECTURE；其余按需。② 每个代码模块开工时先产出 `<模块目录>/CHEATSHEET.md`，只收录该模块用到、owner 可能不熟的技术点。
**理由**：分层加载把接手的上下文成本摁到最低；速查就地消解盲区，不打断学习节奏。
**状态**：生效。

## #5 · 文档写作风格：客观、无对话痕迹

**决策**：活文档只陈述客观事实（系统是什么、为什么这么设计），不带对话痕迹（"owner 已拍板""你问过的"等）。"某决定由谁何时拍板"属溯源信息，归 DECISIONS。
**理由**：活文档面向未来不了解上下文的接手者；溯源与事实分离，各归其位。
**状态**：生效。

---

## #6 · Git 分支策略：main + 功能分支

**决策**：`main` 永远保持可运行；新模块/大改动开 `feat/<名字>` 分支，审过验收后合并回 main，合并点作为章节里程碑。commit message 用 `类型: 简述`（feat/fix/docs/refactor/test/chore）。密钥走环境变量/.env，绝不进提交。
**理由**：符合"一次一个模块"的节奏，天然形成里程碑历史，是生产级协作标准姿势。
**状态**：生效。

---

## #7 · 多工具结果内部粒度：一对一

**决策**：内部统一"一条 tool 消息 = 一个 tool_result 块"，合并/拆分交给 provider 层。
**理由**（官方文档核实）：OpenAI 要求每个 tool_call_id 对应独立 `role:tool` 消息（一对一直接映射）；Anthropic 要求并行工具结果合并进同一条 user 消息（provider 聚合）。一对一粒度最细、最好推理，两个翻译方向都可行。
**状态**：生效。

## #8 · 联网方式：走本地代理

**决策**：需联网核实资料时，用 `curl -x http://127.0.0.1:7890 <url>`（Clash 代理）。
**理由**：内置 WebSearch/WebFetch 在本环境被网络策略阻断；本地代理实测可连通外网。
**注**：代理是否运行取决于 owner 本地环境；端口若变化需重新探测（常见 7890/7897/1080）。
**状态**：生效（依赖 owner 本地代理运行）。

## #10 · 外部设计评审的接纳（合并原 #11/#12/#13）

**背景**：另一 AI 从 agent 工程角度评审了六份设计文档，指出一批时序/短路/一致性类问题。评审原文不归档，接纳的结论在此留痕。

**接纳的关键结论**（已体现在对应活文档中）：
- **system prompt 归属**：内核持有基础 system message（可配置/可空），模块经 `before_model_call` 加工，不替换内核基础部分。（MESSAGE_PROTOCOL §1.1，M0 用到）
- **message.id**：内核用单调自增计数器或 uuid4（实现阶段二选一），无"可复现"约束。
- **call_id**：透传厂商返回值，内核不生成；prompt 模拟的 provider 内部自造并保证同 run 唯一。
- **钩子机制的方向性结论**（拦截链施加顺序、短路规则、REPLACE 泛化、流式下 after_model_call 降级、HALT 补全占位 tool_result、on_error 与防线1 边界）：写入 HOOKS.md 作为**设计设想**，确切机制在 M2 实现时验证敲定。
- **其余就近补入活文档**：token 计数（PROVIDER 可选 count_tokens）、Ctrl-C 处理、上下文溢出为已知限制、config 格式 M3 敲定。

**理由**：评审信噪比高，所指为真实的时序/一致性洞。结论记入活文档即可，无须为"何时落档"反复开决策。
**状态**：生效。

**背景**：设计阶段积累了大量文档（原 1753 行），其中治理规则过度细化、原 #11/#12/#13 三条反复讨论"评审结论何时落档"、活文档把 M2/M4 的实现细节写成"必须照做的权威正文"——后者杜绝了"踩坑学习"的项目初衷。

**决策**：

**理由**：文档应帮助理解、不应替实现拍板未验证的设计。降格后接手者更清楚"哪些已定、哪些开放"，不会误把设想当真相去实现。
**状态**：生效。
