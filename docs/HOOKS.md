# HOOKS — 钩子系统设计

> **状态**：设计设想 · 对齐决策 #1/#10 · 活文档 · 最后更新 2026-07-30
> 钩子系统的设计。内核实现与模块钩子回调以此为方向。
> **注**：本文件的**机制细节（拦截链施加顺序、短路规则、HALT 补全等）是当前设想，M2 实现时验证敲定**——不是必须照抄的硬约束，实现中发现更好的做法可调整并回填本文件（走三件套）。动到钩子系统时读这份。

---

## 0. 心智模型：钩子是什么

**钩子 = 内核在生命周期的关键时机，把控制权短暂交给外部模块的约定接口。**

内核在某个时机广播钩子事件、把当前 `Context` 传过去；监听该钩子的模块回调被依次调用；模块可以只看（观察者）或改数据/改流程（拦截者）。内核不认识任何具体模块——只管时机到了就广播。

钩子调用是**本地函数调用**：微秒级、零 token、零网络。token/延迟只来自模块内部是否调用 LLM。

## 1. 钩子点清单

生命周期顺序排列。

| # | 钩子点 | 触发时机 | 允许权力 | 典型模块 |
|---|--------|---------|---------|---------|
| 1 | `on_run_start` | 一次 run 刚开始，用户输入已入历史 | 观察 / 拦截(改历史) | 可观测、预算初始化、会话记忆加载 |
| 2 | `on_iteration_start` | 每轮循环开始 | 观察 / 拦截(HALT) | 可观测、死循环检测 |
| 3 | `before_model_call` | 消息组装完毕、即将发给模型前 | 观察 / 拦截(改消息) | **RAG 注入**、记忆注入、上下文压缩、prompt 加工 |
| 4 | `after_model_call` | 收到模型响应后 | 观察 / 拦截(改响应，流式下退化为观察，见 §4.1) | 可观测、成本统计、响应缓存 |
| 5 | `before_tool_call` | 即将执行**某一个**工具前（每工具各触发一次） | 观察 / 拦截(SKIP/HALT/REPLACE) | **审批**、预算、参数校验、限流、缓存命中 |
| 6 | `after_tool_call` | **某一个**工具执行完毕后 | 观察 / 拦截(改结果) | 可观测、结果缓存、大输出裁剪 |
| 7 | `on_iteration_end` | 每轮循环结束（本轮工具已处理完） | 观察 / 拦截(HALT) | 记忆写入决策、反思、进度更新 |
| 8 | `on_run_end` | 一次 run 正常结束、即将返回 | 观察 | 可观测、记忆落盘、成本汇总 |
| 9 | `on_error` | 任意环节抛出未被模块自行处理的异常 | 观察 / 拦截(处置建议) | 可观测、错误恢复、降级 |
| 10 | `on_tool_error` | 某个工具执行抛异常 | 观察 / 拦截(处置建议) | 重试、错误恢复 |

**增删钩子点属于内核变更**，走 DECISIONS 记录。宁全勿缺：没人监听的钩子零成本空转。

## 2. 两种权力级别

- **观察者（Observer）**：只读，绝不改流经的数据或流程；多个观察者顺序无关；崩了零影响（防线 2）。例：日志、成本统计。
- **拦截者（Interceptor）**：可改数据或改流程；**必须有明确优先级**（顺序影响结果）；崩了降级处理。例：RAG（改消息）、审批（中断）、缓存（替换）。

一个模块在不同钩子点可扮演不同角色。

## 3. 四个关键问题的解法方向

> 以下是当前设想的方向性结论；确切数据结构与执行细节在 M2 实现时敲定（见 §7 实现参考）。

### A — 拦截者如何修改数据：返回修改指令，由内核施加

**禁止**钩子回调就地改共享数据（不许 `ctx.messages = [...]` 直接篡改）。拦截者**返回一个明确的"修改指令"对象**（如 `modify(append_messages=[...])` / `skip` / `halt` / `replace`），由内核校验后施加。好处：所有修改经内核之手，"谁、何时、改了什么"可追溯、可校验、顺序可控。

**施加顺序**：注入类（RAG/记忆）必须在压缩类**之前**施加，压缩才能压到"含注入内容的完整历史"（MODULES §3）；否则注入内容逃过压缩、可能撑爆窗口。具体施加时机（逐个施加 vs 批量）见 §7。

### B — 错误处理责任人：内核兜底 + 模块可表态 + 内核裁决

- **内核兜底**（永远存在）：任何错误，默认把它转成一条给模型看的消息塞回历史，让模型自己决定下一步。工具报错尤其如此——模型常能自己改参数重试。保证"出错不崩"。
- **模块可表态**：监听 `on_error`/`on_tool_error` 的模块可返回处置建议（retry / halt / feed_model / 不表态）。
- **内核裁决**：收集建议，按固定优先级 **HALT > RETRY > FEED_MODEL** 决定。规则写死在内核，行为可预测。
- **默认**：工具出错默认喂回模型让它自愈，不自动重试；重试交给专门的重试模块（保持内核干净）。

### C — 一次多个工具调用：同步串行，各自独立走钩子

模型一次响应可能返回多个工具调用。规则：
1. 按模型给出的顺序**串行执行**。
2. 每个工具**独立走完整流程**：`before_tool_call` → 执行 → `after_tool_call`；审批/预算能对**每个**工具单独拦截。
3. 某个失败，其余继续执行完，各自成败各自记录。
4. 本轮所有结果**收齐后一起塞回历史**，再进 `on_iteration_end` → 下一轮。

**已知限制**：未来把"串行执行"换成线程池时，"串行→并行"不是无缝替换——并行工具会并发读写同一 Context，产生数据竞争，需加并发保护（锁 / 每工具独立 scratch 副本再合并）。这是一节独立的重构课（决策 #1 只保证"届时可引入"）。

### D — 拦截中断如何传播：三种明确意图

拦截者中断时必须带一个明确意图：

| 意图 | 含义 | 内核动作 | 可用钩子点 | 典型场景 |
|------|------|---------|-----------|---------|
| **SKIP** | 不执行此工具 | 给模型返回"该操作被跳过/拒绝"的工具结果，循环继续 | `before_tool_call` | 审批拒绝 |
| **HALT** | 终止整个 run | 立即停止，控制权交回前端 | 多个钩子点 | 用户急停、预算耗尽 |
| **REPLACE** | 短路真实调用，用拦截者提供的结果代替 | 跳过真实调用，把提供的结果当作产物塞回历史，循环继续 | `before_tool_call`（替工具结果）/ `before_model_call`（替模型响应） | 工具缓存、响应缓存、mock |

**REPLACE 是通用的"短路真实调用 + 提供替代产物"意图**：在 `before_tool_call` 提供替代工具结果；在 `before_model_call` 提供替代模型响应（内核跳过 `provider.chat`）——这是"响应缓存"的落地机制（MODULES §4.3）。SKIP/REPLACE 都让模型"看到一个结果"、agent 继续运转；HALT 是唯一会终止 run 的中断。

## 4. 执行顺序与流式降级

同一钩子点挂多个模块时按**优先级数字升序**执行（数字小的先，具体升/降序在实现时定死）。观察者顺序无关但仍走排序以保证可复现；拦截者顺序敏感（"RAG 注入"在"压缩"之前还是之后须由优先级明确）。每个模块在 `MODULES.md` 登记优先级。

### 4.1 流式路径下 `after_model_call` 降级

- **非流式**（`provider.chat`）：响应一次性拿到再触发，"改响应/替换"都有意义——完整语义。
- **流式**（`provider.chat_stream`）：响应已逐 token 显示给用户，`after_model_call` 在流结束后才触发，"改响应"物理上无意义。故流式下 `after_model_call` **退化为纯观察者**，改响应类拦截者自动失效降级并记 trace，不报错。

"替换响应"的需求（如响应缓存）在流式下由 `before_model_call` 的 REPLACE 在**调用前**短路承担，两条路径走同一条正确逻辑。M0 只用非流式 `chat`，不触发此降级。

## 5. 四道防线（爆炸半径控制）

模块在回调里崩溃/返回脏数据可能污染主流程。四道防线把"毁灭性"降级为"某模块失效"：

1. **沙箱化调用**（最重要）：内核调用任何钩子回调都包错误捕获。模块抛异常 → 内核捕获、记 trace、按策略继续。**一个模块的失败绝不允许掀翻内核。**
2. **按角色降级**：观察者崩了零影响；拦截者崩了当这次拦截没发生过，用原始数据继续（如 RAG 崩了 = 本轮无检索，退化成普通 agent）。
3. **数据校验**：拦截者返回的修改指令，内核施加前先校验合法性（改后 messages 仍合法、REPLACE 结果符合格式）；不过则拒绝该修改、记警告、降级继续。
4. **全程可观测**：每次"崩溃降级/修改被拒/中断施加"都产生 trace，前端能看到 `⚠️ RAG 模块本轮失败，已跳过`。

**防线 1 与 `on_error` 的边界**：钩子回调自身崩溃 → 防线 1 处理（记 trace + 按角色降级），**不触发 `on_error`**（否则钩子崩溃引发 on_error、on_error 又是钩子又崩……形成钩子风暴）；provider/工具/主循环骨架崩溃 → 触发 `on_error`；`on_error` 处理器自身崩溃 → 防线 1 兜住，绝不递归。

## 6. 内核发出结构化事件流（可观测性作为一等公民）

内核在每个钩子点、每次修改施加、每次降级时都发出**结构化事件（trace event）**。这是内核内建能力，不依赖任何模块；"可观测性模块"只是这些事件的一个消费者/美化展示者。即使不挂任何模块，内核自己也在产生事件流，供 CLI 直接显示、供 debug。事件至少含：时间序号、钩子点、模块名、动作类型、摘要（确切字段在实现时与 MESSAGE_PROTOCOL 一并定）。

## 7. 实现参考（M2 验证后敲定）

> 以下是设计阶段推演的机制，供 M2 实现参考。**尚未经代码验证，实现时可调整**，调整后回填本节并走三件套。

**拦截链执行模型（设想：逐个施加）**：
```
sorted_interceptors = sort_by_priority(interceptors)   # 升序，数字小者先
for interceptor in sorted_interceptors:
    result = interceptor(ctx)          # ctx 已含前面拦截者施加的修改
    if result is None: continue        # 观察者 / 不改
    validate(result)                   # 防线 3：非法则拒绝、记警告、降级继续
    ctx = apply(result, ctx)           # 立即施加，记 trace
    if result.is_terminal(): break     # SKIP/HALT/REPLACE 短路其余
```
选"逐个施加"而非"收集完再统一施加"的理由：注入类（优先级 100 段）须在压缩类（200 段）之前施加，压缩才能压到含注入内容的完整历史；若统一 apply，压缩看到的是未注入的原始历史。

**短路规则（设想）**：同一钩子点升序执行，第一个返回终止意图（SKIP/HALT/REPLACE）者胜出并短路其余；modify/None 不短路。由此同一工具上审批（@300）排在缓存（@400）之前——审批拒绝会短路，被拒的调用自然不查缓存。

**HALT 落在多工具批次中途（设想）**：OpenAI/Anthropic 都要求每个 tool_call 必须有配对 tool_result 才能发下一条消息。故 HALT 时内核为该轮所有**未执行的 tool_call** 各补一条 `tool_result(is_error=True, content="aborted: run halted")` 占位，保证配对完整、历史合法可续跑，再终止 run。

**待实现阶段敲定**：`HookResult`/`ErrorAction` 的确切类型；优先级升/降序与默认值；trace event 字段（与 MESSAGE_PROTOCOL 一起定）；死循环检测挂 `on_iteration_start` 用什么信号判定（最大迭代数已是内核安全阀）。
