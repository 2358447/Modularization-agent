## 0. 心智模型：钩子到底是什么

一句话：**钩子 = 内核在生命周期的关键时机，把控制权短暂交给外部模块的"约定接口"。**

- 内核在某个时机"广播"一个钩子事件，并把当前 `Context` 传过去。
- 监听该钩子的模块回调被依次调用。
- 模块可以只看（观察者），也可以改数据/改流程（拦截者）。
- **内核不认识任何具体模块**——它只管在时机到了广播，谁在听、听了干什么，内核不关心。

钩子调用是**本地函数调用**：微秒级、零 token、零网络。token/延迟只来自模块内部是否调用 LLM，与钩子机制本身无关。

## 1. 钩子点权威清单

生命周期顺序排列。每个钩子点标注：触发时机、传入什么、允许的权力级别（见第 2 节）。

| # | 钩子点 | 触发时机 | 允许权力 | 典型模块 |
|---|--------|---------|---------|---------|
| 1 | `on_run_start` | 一次 run 刚开始，用户输入已入历史 | 观察 / 拦截(改历史) | 可观测、预算初始化、会话记忆加载 |
| 2 | `on_iteration_start` | 每轮循环开始 | 观察 / 拦截(HALT) | 可观测、死循环检测 |
| 3 | `before_model_call` | 消息组装完毕、即将发给模型前 | 观察 / 拦截(改消息) | **RAG 注入**、记忆注入、上下文压缩、prompt 加工 |
| 4 | `after_model_call` | 收到模型响应后 | 观察 / 拦截(改响应) | 可观测、成本统计、响应缓存 |
| 5 | `before_tool_call` | 即将执行**某一个**工具前（每个工具各触发一次） | 观察 / 拦截(SKIP/HALT/REPLACE) | **审批**、预算拦截、参数校验、限流、缓存命中 |
| 6 | `after_tool_call` | **某一个**工具执行完毕后 | 观察 / 拦截(改结果) | 可观测、结果缓存、大输出裁剪 |
| 7 | `on_iteration_end` | 每轮循环结束（本轮所有工具已处理） | 观察 / 拦截(HALT) | 记忆写入决策、反思、进度更新 |
| 8 | `on_run_end` | 一次 run 正常结束、即将返回 | 观察 | 可观测、记忆落盘、成本汇总 |
| 9 | `on_error` | 任意环节抛出未被模块自行处理的异常 | 观察 / 拦截(处置建议) | 可观测、错误恢复、降级策略 |
| 10 | `on_tool_error` | 某个工具执行抛异常 | 观察 / 拦截(处置建议) | 重试策略、错误恢复 |

**增删钩子点属于内核变更**，必须走 DECISIONS.md 记录。宁全勿缺：没人监听的钩子零成本空转。

## 2. 两种权力级别

### 观察者（Observer）
- **只读**，绝不改变流经的数据或流程。
- 多个观察者**顺序无关**（谁先谁后不影响正确性）。
- 崩了 **零影响**（见防线 2）。
- 例：可观测性、日志、成本统计。

### 拦截者（Interceptor）
- 可以**修改数据**或**改变流程**。
- **必须有明确优先级**（见第 4 节），因为顺序影响结果。
- 崩了会降级处理（见防线 2）。
- 例：RAG（改消息）、审批（中断流程）、缓存（替换结果）。

> 一个模块在不同钩子点可以扮演不同角色：RAG 在 `before_model_call` 是拦截者，在 `on_run_end` 可能只是观察者。

## 3. 硬伤解法

### 硬伤 A — 拦截者如何修改数据：**返回修改，内核统一施加**

**禁止**钩子回调就地改共享数据（不许 `ctx.messages = [...]` 直接赋值篡改）。
**要求**拦截者**返回一个明确的"修改指令"对象**，内核按优先级顺序逐个施加，并为每次施加记一条 trace。

修改指令的形态（示意，实现细节见内核代码阶段）：

```
# 观察者：返回 None（什么都不改）
return None

# 拦截者改消息（before_model_call）：返回一个修改指令
return HookResult.modify(messages=新的消息列表)      # 替换
return HookResult.modify(append_messages=[...])       # 追加（更常见，RAG 用）

# 拦截者中断（before_tool_call）：见硬伤 D
return HookResult.skip(reason="用户拒绝")
return HookResult.halt(reason="预算耗尽")
return HookResult.replace(result=缓存结果)
```

**内核施加修改时的动作**：
1. 按优先级排序拦截者，依次取其返回的修改指令。
2. 每施加一个，记 trace：`[hook=before_model_call][module=rag][prio=100] append_messages(2条)`。
3. 施加前**校验**（防线 3）：改完的 `messages` 仍是合法结构吗？非法则拒绝该修改、记警告、降级继续。

**设计理由**：所有修改经内核之手，"谁、何时、改了什么"可追溯。代价是模块不能就地改、需返回指令，换来可控顺序、可追溯、可校验。

---

### 硬伤 B — 错误处理责任人：**内核兜底 + 模块可升级 + 内核裁决**

三层结构，从下到上：

**① 内核兜底（永远存在，最稳的底）**
任何错误，内核默认行为 = **把错误转成一条给模型看的消息塞回历史**，让模型自己决定下一步。
- 工具报错尤其如此——模型常能自己改参数重试。
- 这是 agent 标准做法，保证"出错不崩"。

**② 模块可表态（可选）**
监听 `on_error` / `on_tool_error` 的模块可返回"处置建议"：
```
return ErrorAction.retry(max=3)      # 建议重试
return ErrorAction.halt(reason=...)  # 建议终止整个 run
return ErrorAction.feed_model()      # 显式选择默认：喂回模型
return None                          # 不表态，交内核默认
```

**③ 内核裁决（说了算）**
内核收集所有建议，按**固定优先级**决定最终动作：

> **HALT（终止） > RETRY（重试） > FEED_MODEL（喂回模型，默认兜底）**

即：只要有一个模块要求终止，就终止；否则若有模块要求重试，就重试；否则走默认——喂回模型。规则写死在内核，行为可预测。

**默认策略**：
- 工具出错，**默认直接喂回模型让它自愈**，不自动重试。
- 重试能力交给**专门的重试模块**（按需挂载，保持内核干净）。

---

### 硬伤 C — 一次多个工具调用：**同步串行，各自独立走钩子，全部收齐再进下一轮**

模型一次响应可能返回多个工具调用。处理规则：

1. **按模型给出的顺序，串行执行**（同步内核的自然选择，也让每一步清晰可见）。
2. **每个工具独立走完整流程**：`before_tool_call`（可对该工具单独 SKIP/HALT/REPLACE）→ 执行 → `after_tool_call`。
   - 意味着审批/预算能对**每一个**工具单独拦截（批准工具1、拒绝工具2）。
3. 多个工具中某个失败，**其余继续执行完**，各自成败各自记录（工具间通常独立）。
4. 本轮**所有工具结果收齐后，一起塞回历史**，再进入 `on_iteration_end` → 下一轮。

**未来并行**：把"串行执行这一段"换成线程池即可，钩子契约不变——这是同步不锁死未来的体现（决策 #1）。

---

### 硬伤 D — 拦截中断如何传播：**三种明确意图**

拦截者在 `before_tool_call` 中断时，**必须带一个明确意图**，内核据此走分支。三种意图如下：

| 意图 | 含义 | 内核动作 | 典型场景 |
|------|------|---------|---------|
| **SKIP** | 不执行此工具 | 给模型返回一条"该操作被跳过/拒绝"的工具结果消息，**循环继续** | 审批拒绝 |
| **HALT** | 终止整个 run | 立即停止，控制权交回前端 | 用户急停、预算彻底耗尽 |
| **REPLACE** | 不执行真实工具，用拦截者提供的结果代替 | 把提供的结果当作该工具结果塞回，**循环继续** | 缓存命中、mock 测试 |

- **SKIP** 和 **REPLACE** 都让模型"看到一个结果"（一个是拒绝说明，一个是替代结果），agent 继续运转。
- **HALT** 是唯一会终止 run 的中断。
- 三种意图覆盖了"拒绝 / 急停 / 命中替代"三类真实场景；如遇第四类场景，属内核变更，走 DECISIONS 记录。

## 4. 执行顺序（优先级）

- 同一钩子点挂多个模块时，按**优先级数字**升序执行（数字小的先执行；具体升/降序在内核实现时定死并写明）。
- **观察者**顺序无关，但仍统一走优先级排序以保证可复现。
- **拦截者**顺序敏感：例如"RAG 注入"应在"上下文压缩"之前还是之后，必须由优先级明确决定，不留玄学。
- 每个模块在 `MODULES.md` 中登记它在各钩子点的优先级，形成全局可查的优先级表。

## 5. 四道防线（爆炸半径控制）

钩子架构的风险：模块在回调里崩溃/返回脏数据/死循环，可能污染主流程。四道防线把"毁灭性"降级为"某模块失效"。

### 防线 1 — 沙箱化调用（最重要）
内核调用**任何**钩子回调都包一层错误捕获。模块在钩子里抛异常 → 内核捕获它、记一条错误 trace、按策略继续。**一个模块的失败绝不允许掀翻内核。**

### 防线 2 — 按角色降级
- **观察者**崩了 → **零影响**，只读不改流程，记"该观察者失败"后继续。
- **拦截者**崩了 → 内核**默认当这次拦截没发生过**，用未修改的原始数据继续。
  - 例：RAG 崩了 = 本轮没做检索，agent 退化成无外部知识的普通 agent，**功能降级但不崩溃**（铁律 3"优雅降级"）。

### 防线 3 — 数据校验
拦截者返回的修改指令，内核施加前先校验合法性（如"改后的 messages 仍是合法结构""REPLACE 的结果符合工具结果格式"）。校验不过 → 拒绝该修改、记警告、降级继续。**脏数据进不了主流程。**

### 防线 4 — 全程可观测
每一次"模块崩溃被降级""修改被拒""中断被施加"都产生一条 trace。前端能看到 `⚠️ RAG 模块本轮失败，已跳过`。**出问题时一眼知道是谁、在哪、怎么降级的**，绝不神秘崩溃。

> 对比：若把 RAG/记忆等能力硬编码进主循环，单个 bug 会波及整个内核且无降级机制。钩子架构将风险隔离、可控。

## 6. 内核发出结构化事件流（可观测性作为一等公民）

（对应 ARCHITECTURE 开放问题 F）

内核在每个钩子点、每次修改施加、每次降级时，都发出**结构化事件（trace event）**。
- 这是内核**内建**能力，不依赖任何模块。
- "可观测性模块"只是这些事件的一个**消费者/美化展示者**；即使不挂任何模块，内核自己也在产生事件流，供 CLI 直接显示、供 debug。
- 这让"看清每一步"成为框架的地基能力，而非可选插件。

事件至少含：时间序号、钩子点、模块名、动作类型、摘要。（具体字段在写内核时定，与 MESSAGE_PROTOCOL 一并设计。）

---

## 7. 模块侧契约（预告，详见 MODULES.md）

一个模块声明：
- 监听哪些钩子点、各自优先级、扮演观察者还是拦截者。
- 回调签名：`(ctx: Context) -> HookResult | None`（同步）。
- 只通过 `Context` 读写数据，不私下互传（铁律 5）。
- 必须能优雅降级（不假设别的模块存在）。

`HookResult` / `ErrorAction` 的确切类型定义，留到写内核代码时与 MESSAGE_PROTOCOL 一起敲定。
